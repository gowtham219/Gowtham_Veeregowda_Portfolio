LeadForge / PROSPECTING & GTM

Turn scattered business listings into usable prospect data.

01

A prospecting workspace that joins business discovery, contact extraction, quality checks and historical deduplication into a repeatable research workflow.

Python · Flask · SQLAlchemy · SQLite · Playwright · Pandas

Business purpose. Give sales and marketing teams an organised starting point for outreach, with visibility into what was discovered and what is genuinely new.
WorkflowDatabase & storageImplementation evidence

The workflow cycle

  1. Search briefEnter a business / location query or upload a batch workbook.
  2. Discover businessesCollect listing information and website links; a Places API path is available when configured.
  3. Extract contactsVisit websites, extract email addresses and telephone numbers, then clean and prioritise the results.
  4. Compare and retainCompare against the reference database; separate previously known contacts from new records.
  5. Review and exportDownload structured Excel outputs; inspect new-lead counts, run outcomes and reference growth.
  6. Repeat safelyReuse the reference store for the next campaign. Batch progress and checkpoint files support interrupted runs.

Database & storage model

SQLite reference database + JSON history + Excel outputs

Batch / phase checkpointsinput fingerprint, completed work, partial progressFile-based recovery state; separate from the reference database.
Excel + run logsprospect exports and timestamped processing logsDownloadable business outputs and troubleshooting history.

Business Suite / SALES INTELLIGENCE

Make sales and account activity easier to act on.

02

A Windows desktop dashboard launches reporting and document tools for sales, collections, customer statements and account follow-up.

Python · Desktop dashboard · Pandas · Excel / PDF / Word · Outlook COM

Business purpose. Translate spreadsheet records into sales trends, account movement and review-ready reports, with Outlook drafts kept under human control.
WorkflowDatabase & storageImplementation evidence

The workflow cycle

  1. Choose a business taskSelect sales reporting, receivables, statements, collections or another registered tool.
  2. Load source filesThe selected Python script reads its required workbooks and prepares structured data.
  3. Calculate and compareAggregate by customer, salesperson, category and product; compare complete months and flag account movement.
  4. Produce reportsCreate task-specific Excel, PDF or Word output and, where supported, a mail queue.
  5. Review communicationCreate Outlook drafts with report attachments. The reviewed sales-mail path saves drafts rather than automatically sending.
  6. Follow up and rerunA person reviews the findings and contacts accounts; the next source workbook feeds the next reporting cycle.

Database & storage model

Spreadsheet inputs + generated files + JSON queues / preferences

Store / entityData heldRole in the workflow
Source workbookscustomer, salesperson, product, category and transaction dataInputs vary by reporting tool; the portfolio includes no customer records.
Generated reportsaggregated sales, balances, movements and operational summariesOutput files are the reporting products; no common relational database was identified.
Mail queue JSONrecipient fields, subject, HTML body, attachment referencesIntermediate draft instructions consumed by the Outlook draft creator.
Dashboard settingssaved UI / tool state and theme preferencesApplication preferences, not a central customer master.

DocuFlow / DOCUMENT OPERATIONS

Give repetitive document work a consistent workflow.

03

A Flask interface runs registered Python tools for delivery orders, invoices, reference matching, renaming, merging and workbook splitting. The archive contains both a basic version and a multi-user version; this map describes the multi-user implementation.

Python · Flask · Subprocess workers · PDF / spreadsheet utilities

Business purpose. Organise document processing around named tools, user-specific folders and visible run history instead of repeated manual file handling.
WorkflowDatabase & storageImplementation evidence

The workflow cycle

  1. Sign inResolve the account, its active/hold state and permitted tools.
  2. Choose a toolSelect one of seven registered workflows; the app checks tool permission and hold state.
  3. Start a workerLaunch a Python subprocess with the user’s root and status-file paths. The per-user guard prevents overlapping tracked jobs.
  4. Process documentsThe chosen script reads the relevant PDFs or workbooks and writes its output folder.
  5. Monitor completionThe interface polls status and history; completion or unexpected exit is recorded.
  6. Review the outputOpen the output folder, inspect results, then launch the next relevant tool.

Database & storage model

JSON users + per-user status/history + document folders

Per-user history JSONtool, result, timestamp and duration where availableThe multi-user app retains the most recent 50 runs per user.
User root foldersinput and processed PDFs / workbooksDocument content stays in files; subprocess environment supplies the folder context.

Delivery Management / FULFILMENT & REQUESTS

Keep delivery progress and item requests visible.

04

A portal launches two separate Flask applications: delivery tracking and internal item requests. Each tool has its own SQLite database and session cookie.

Python · Flask · Flask-SQLAlchemy · SQLite · Pandas

Business purpose. Give operations teams a shared way to monitor deliveries, record exceptions and progress item requests within role-specific controls.
WorkflowDatabase & storageImplementation evidence

The workflow cycle

  1. Open the portalThe launcher starts the two tools and routes the user to the selected application.
  2. Delivery intakeAdmin/SOP roles add or import delivery records; the store view updates delivery details within its permissions.
  3. Track delivery statesFilter warehouse, out-for-delivery, partial, pending, delivered and returned records; record driver and reason.
  4. Request intakeSOP users submit item requests using workbook-backed item lookup; visibility is scoped by role and staff identity.
  5. Arrange and closePurchase staff update arrangement status; SOP/admin closure records a closed timestamp.
  6. Review and exportSearch, filter and export records; the two databases remain separate.

Database & storage model

data.db for deliveries + item_request.db for requests/users

Store / entityData heldRole in the workflow
Delivery model → data.dbid, do_no, client_name, location, prepared_date, driver, status, reasonDelivery records and operational status.
ItemRequest model → item_request.dbrequest time, requester, item, quantity, status, remarks, closed timeSeparate request lifecycle; closure is stored explicitly.
User model → item_request.dbusername, password_hash, role, staff_name, display_namePer-person request access. Delivery tracking has a separate account mechanism.
Reference workbookitem code, description and referenceLoaded for item lookup; not a shared ERP master connection.

State transitions and role boundaries

Delivery: records may be In Warehouse, Out for Delivery, Partial Delivery, Pending, Delivered or Not Delivered/Returned. The UI groups older open records as pending and keeps partial deliveries in a dedicated tab.

AMC Management / CUSTOMER LIFECYCLE

Connect contracts, consumption and after-sales service.

05

A Flask application models customer accounts, contracts, installations, chemical dosing requirements, equipment, service work and complaints. A configurable API client imports ERP delivery-note quantities for consumption monitoring.

Python · Flask · SQLAlchemy · SQLite · REST APIs · APScheduler

Business purpose. Create a traceable operational view of what is installed, what is due, what has been consumed and what requires customer follow-up.
WorkflowDatabase & storageImplementation evidence

The workflow cycle

  1. Create the commercial recordRegister customers and products, then create/import contracts and their equipment or chemical requirements.
  2. Set the consumption requirementMatch purchases by product category or exact item; calculate required quantities for the installation or dosing setup.
  3. Import consumptionManually sync the configured REST API or use Excel. Optional scheduling can invoke sync; source records are aggregated before upsert.
  4. Evaluate the accountCompare recorded quantities with minimum requirements; inspect customer profiles, sales views and renewal dates.
  5. Deliver serviceSchedule work, assign technicians, record visits and attachments, and track complaints through resolution.
  6. Renew and retain historyReview expiry alerts and renewals. Preserve service reports, equipment timelines and activity records.

Database & storage model

Relational SQLite models + uploaded documents + exports

Store / entityData heldRole in the workflow
Customer and commercial modelsCustomer, ProductCategory, Product, Contract, ChemicalContractCustomer owns contracts; contract-specific salesperson attribution is used in sales views.
Consumption and requirementsInstallation, Consumption, ChemicalMOQConsumption links customers/products and is matched by month, optionally site, then category or item.
Equipment and serviceMachine, MachineDocument, ServiceRecord, ServiceReport, ServicePhoto, ServiceAttachment, TimelineEventService targets use target_type + target_id for multiple kinds of equipment; these are application-level references.
Governance and communicationUser, RolePermission, AccessRequest, OneTimeAccessGrant, ActivityLog, ChatMessage, ChatReadRole/module permissions, temporary elevated access, messaging and audit records.
Complaints and filesComplaint, Document, uploaded files and exportsComplaint intake includes an optional Microsoft Forms / Power Automate webhook path; files are separate from database metadata.

Machine Register / ASSET & SERVICE HISTORY

Make every equipment record tell its service story.

06

A Flask and SQLite register for customers, machines, warranty dates, technician assignments, visit records, attachments and printable service reports.

Python · Flask · sqlite3 · Excel import/export · HTML reports

Business purpose. Keep equipment and service information together so teams can understand what happened, who attended and what should happen next.
WorkflowDatabase & storageImplementation evidence

The workflow cycle

  1. Register equipmentCreate or import customers and machines; record serial, sale date and warranty period.
  2. Plan a visitAdd service work with planned timing, status, location and technician assignments.
  3. Record the workCapture actual time, findings, work completed and recommendations; attach supporting documents.
  4. Associate people and filesThe service-to-technician join supports multiple technicians; file metadata points to stored attachments.
  5. Generate a reportOpen the service or machine report for printing; review activity and technician history.
  6. Continue the lifecycleAdd the next visit and preserve prior records. Backup uses a database snapshot plus uploaded files.

Growth opportunities

Scale the process, then measure the impact.

The code demonstrates practical building blocks. The next stage would validate reliability, adoption and commercial outcomes in a defined operating environment.

Connect with clear ownership

Define who owns customer, product and equipment records. Use explicit mapping rules and versioned APIs rather than letting separate applications write directly into one another’s databases.

Make execution durable

Move long-running work into persistent queues where needed. Add retry policies, duplicate-safe writes, monitoring and recovery tests. Measure workload before selecting a different database or deployment model.

Measure business outcomes

For LeadForge, measure usable-contact yield and time per reviewed prospect. For reporting, measure preparation time and follow-up actions. For operations, measure overdue work, cycle time and rework.

Prepare a shareable demonstration

Use synthetic customer and transaction records. Show one complete workflow per application, including an exception path, so a reviewer can see how the system behaves without accessing live business data.

No revenue increase, time-saving percentage, production user count or load capacity is claimed here. Those outcomes require a measured baseline and deployment evidence.
